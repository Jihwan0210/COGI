**1~3번은 최종 포트폴리오에서 결제 사례 하나로 묶을 수 있다.** 6개 소제목을 모두 이력서에 나열할 필요는 없다. 우선 결제와 게스트를 완성하고, 통계 또는 메일에서 증거가 좋은 사례를 추가한다.

각 절은 `현재 코드 확인 → 정책 결정 → 대안 비교 → 변경 전 재현 → 구현 → 검증 → 기록` 순서다. 정책을 선택했다는 기록과 테스트 통과를 구분한다.

**부하 테스트도 진행한다.** 통합·동시성 테스트는 정확성을, 부하 테스트는 요청량에 따른 지연·오류·자원 사용을 확인한다. 7번의 설계·변경 전 측정은 0번 준비 직후 시작하고, 각 개선 완료 후 변경 후 측정을 한다. 선택 사항인 공지 메일 작업이 끝날 때까지 기다릴 필요는 없다.

### 1-3. 아래 대안을 비교하고 현재 선택을 설명한다

| 후보 | 장점 | 감수할 점 | 이 프로젝트에서의 판단 |

- [ ] 승인 응답을 현재 처리 코드가 보관하지 않으며 매 호출마다 새 UUID 주문번호를 만든다는 점을 기록한다.
- [ ] `BillingScheduler`가 예외 종류를 구분하지 않고 강등을 시도하는지 확인한다.

### 2-2. 다음 두 장애를 변경 전에 재현한다

- [ ] 결제 테스트 서버는 승인을 저장하지만 응답을 끊도록 한다. 애플리케이션은 결과를 모르는 상태가 된다.
- [ ] 다른 테스트에서는 결제 승인을 정상 반환하고 그 뒤 DB 최종 반영을 실패시킨다. 승인 단계의 성공 사실은 테스트 서버에서 따로 조회할 수 있게 한다.
- [ ] 외부 승인 결과와 DB의 구독 상태를 나란히 저장한다. 실제 발생한 운영 장애인지 테스트로 주입한 장애인지 구분한다.

**확인할 문제:** DB 롤백이 외부 승인을 취소하지 않는데, 애플리케이션이 모든 예외를 미승인으로 해석하고 있지 않은가?

### 2-3. 구현 전에 오류별 정책을 확정한다

| 상황 | 권장 출발 정책 | 직접 결정할 내용 |
|---|---|---|
| 결제사에서 확정 거절 | 거절 상태 기록, 사용자 안내 | 즉시 FREE 또는 짧은 유예기간 |
| 타임아웃·응답 유실 | UNKNOWN 기록, 승인 결과 조회 | 조회 간격·확인 기한 |
| 승인 확인 후 DB 반영 실패 | 동일 작업을 찾아 로컬 반영 복구 | 복구 주기·최종 수동 확인 절차 |
| 조회 서비스 장애 | UNKNOWN 유지, 나중에 조회 | 사용자에게 표시할 대기 상태·알림 |
| 잘못된 설정·키·코드 오류 | 운영 오류로 분류, 자동 청구 반복 중단 | 기록·수동 복구 조건 |

- [ ] 확정 거절에 대한 FREE 전환은 기존 정책 유지로 시작할지 적는다. 새로운 유예 정책을 선택하면 접근 권한과 사용자 안내도 함께 정의한다.
- [ ] “재시도 3회”의 대상이 승인 요청인지 조회 요청인지 구분한다. 첫 구현은 **결과 조회·로컬 반영 복구**부터 만든다.
- [ ] 확인 불가 상태를 임의로 실패 확정하지 않는다. 유예 종료 시 사용 권한 처리와 미확정 청구의 추적은 별개로 정의한다.

### 2-4. 같은 문제를 푸는 대안을 비교한다

| 후보 | 장점 | 대가 | 권장 판단 |
|---|---|---|---|
| 예외면 강등하고 다음에 새 승인 | 구현 단순 | 이미 승인된 건도 강등·중복 승인 위험 | 결과 불명에 적용하지 않음 |
| DB 청구 작업 + 결제사 조회 | 기존 DB 활용, 중단 지점 추적·복구 가능 | 상태 모델·복구 코드 필요 | 현재 프로젝트의 우선 후보 |
| 메시지 큐로 작업 전달 | 소비자 분리·버퍼링 | 브로커 운영, 중복 전달 처리·결제 멱등성은 여전히 필요 | 현재 요구만으로 필수 도입하지 않음 |

- [ ] “DB 작업 기록으로 시작한다”는 선택 이유와 실패 복구 복잡도가 늘어난다는 대가를 적는다.

### 2-5. 청구 작업 데이터와 상태를 설계한다

- [ ] 구독 변경 이력과 청구 작업을 구분한다. 새 엔티티 이름은 `BillingJob`을 권장하며 기존 `SubscriptionHistory`는 변경 이력 용도를 유지한다.
- [ ] 다음 필드의 타입·null 허용·인덱스·보관 정책을 정한다.

| 필드 | 용도 |
|---|---|
| id, subscriptionId, billingType, periodDueAt | 같은 청구 의도 식별. 주기는 최초 대상 선정 때의 납기 기준 |
| amount, planId, paymentMethodId | 승인할 금액·플랜·결제수단의 스냅샷 또는 참조 |
| orderId, idempotencyKey | 해당 승인 시도에 대해 한 번 생성·저장 후 재사용 |
| status, paymentKey | 작업 상태와 확인한 외부 승인 식별자 |
| attemptCount, lookupCount, nextCheckAt | 승인 시도와 조회 시도 구분, 복구 시각 |
| errorCode, errorMessage, createdAt, updatedAt | 원인과 경과 추적 |
| version 또는 ownerToken/leaseUntil | 3번에서 동시 처리·오래된 작업자의 변경을 제어 |

- [ ] 상태를 `PREPARED`, `PROCESSING`, `UNKNOWN`, `SUCCEEDED`, `DECLINED`, `MANUAL_REVIEW`로 시작한다. 명칭은 바꿔도 각 의미는 문서화한다.
- [ ] `PREPARED → PROCESSING → SUCCEEDED/DECLINED/UNKNOWN`, `UNKNOWN → 조회 → SUCCEEDED/DECLINED/UNKNOWN/MANUAL_REVIEW` 전이를 정의한다.
- [ ] `SUCCEEDED` 작업을 다시 연장하거나 실패 상태로 덮어쓰지 못하게 한다.
- [ ] UNIQUE는 `subscriptionId + billingType + periodDueAt`처럼 실제 청구 의도를 기준으로 둔다. 서버 실행 시각의 월을 키로 쓰지 않는다.
- [ ] DDL 변경을 재실행 가능한 마이그레이션으로 남긴다. 운영 데이터가 있다면 기존 행 충돌 여부와 적용 순서를 먼저 확인한다.

여러 번의 확정 거절 후 새 승인 시도를 허용하려면 `BillingJob` 아래에 시도별 `BillingAttempt` 기록을 추가하는 식으로 구분한다. 처음부터 모든 거절을 자동 재청구하는 기능은 붙이지 않는다.

### 2-6. 아래 순서로 코드를 나눈다

1. [ ] 스케줄러는 구독 ID와 원래 납기를 전달하도록 한다.
2. [ ] 짧은 트랜잭션의 준비 메서드에서 청구 대상·해지·상태를 확인하고 청구 작업·금액·식별자를 저장한다.
3. [ ] 준비 메서드가 반환되기 전에 커밋되게 한다. 단순 `saveAndFlush()`는 커밋이 아니라는 점을 확인한다.
4. [ ] 외부 트랜잭션 없는 처리 조정 메서드에서 승인 호출을 수행한다. DB 커넥션을 붙잡고 네트워크 응답 전체를 기다리지 않도록 한다.
5. [ ] `TossPaymentClient`에 저장된 멱등키를 전달한다. 해당 승인 시도의 같은 요청은 같은 주문번호·금액·결제수단을 사용한다.
6. [ ] 승인 응답의 상태·금액·주문번호를 검증하고, 별도 트랜잭션의 성공 확정 메서드에서 작업 성공·구독 연장·이력을 함께 반영한다.
7. [ ] 타임아웃은 UNKNOWN으로 기록하고 확정 거절만 선택한 거절 정책으로 보낸다. DB 장애로 UNKNOWN 기록도 실패하면 남은 PROCESSING 작업을 이후 복구가 찾도록 한다.
8. [ ] 성공 알림은 성공 커밋 이후에 보내도록 옮긴다. 알림 실패로 결제 상태를 실패로 바꾸지 않는다.

권장 책임 이름은 `BillingCoordinator`, `BillingJobService`, `BillingRecoveryService`다. 반드시 이 수만큼 클래스를 만들 필요는 없지만, **프록시를 경유하는 DB 경계와 외부 호출 경계**는 명확해야 한다.

토스의 멱등키 적용 범위·유효기간과 오류 응답을 확인한다. 유효기간이 지난 UNKNOWN 작업에 새 키로 무조건 승인 요청을 보내지 않는다. [토스 멱등키 문서](https://docs.tosspayments.com/reference/using-api/authorization)

### 2-7. 상태 조회와 복구를 구현한다

- [ ] 주문번호를 기준으로 결제 결과를 조회하는 클라이언트 메서드를 추가한다. [토스 결제 조회 API](https://docs.tosspayments.com/reference)
- [ ] 승인 확인 시 승인된 금액·주문번호를 검증하고 동일한 성공 확정 메서드를 사용한다.
- [ ] 조회 결과 없음·조회 실패·처리 중을 구분한다. 한 번의 조회 실패로 미승인을 확정하지 않는다.
- [ ] 오래된 PROCESSING과 확인 시각이 된 UNKNOWN 작업을 조회하는 복구 메서드를 만든다. 처음에는 테스트에서 직접 호출한다.
- [ ] 조회 재시도 간격과 횟수 제한을 설정으로 빼고, 상한 도달 시 MANUAL_REVIEW에 남긴다.
- [ ] 수동 확인은 미확정 목록 조회 → 결제사 결과 확인 → 같은 확정 메서드 호출 순서로 둔다. 인증 없이 접근 가능한 복구 API를 만들지 않는다.
- [ ] 복구 테스트가 통과하면 스케줄 실행을 연결한다. 동시 실행 제어는 3번에서 함께 마무리한다.

### 2-8. 아래 통합 테스트를 모두 통과시킨다

권장 테스트 이름: `BillingRecoveryIntegrationTest`.

| 장애 주입 위치 | 기대 결과 |
|---|---|
| 작업 저장 직후 종료 | 재시작 후 작업을 발견하고 정책에 따라 재개 |
| 승인 성공 후 응답 유실 | 조회로 승인 확인, 외부 승인 효과 1회, 강등 없음 |
| 승인 성공 후 DB 반영 실패 | 외부 재승인 없이 로컬 구독·이력 복구 |
| 결제사 확정 거절 | DECLINED 및 선택한 권한 정책 적용 |

- [ ] 외부 HTTP 호출 횟수와 실제 승인 효과 수를 따로 센다. 멱등 재전송 때문에 호출은 여러 번일 수 있다.
- [ ] 최초 구독과 업그레이드의 같은 위험을 별도 후속 항목으로 기록한다. 이 절이 정기 결제만 개선했다면 그렇게 범위를 쓴다.

**완료 조건:** 성공·거절·결과 불명을 구분하고, 미확정 작업을 남겨 재기동 후 복구할 수 있다. 3번 동시성 검증 전에는 여러 서버에서 안전하다고 쓰지 않는다.

## 3. 여러 서버의 중복 청구를 실행 잠금으로 막을까, 청구 단위로 막을까?

### 3-1. 서로 다른 두 보장을 구분한다

- [ ] 스케줄러 잠금은 “지금 배치를 동시에 실행하는 수”를 줄인다고 적는다.
- [ ] 청구 멱등성은 “같은 납기의 결제가 반복 처리돼도 승인·연장을 중복하지 않는 것”이라고 적는다.
- [ ] 스케줄러 재실행·잠금 만료·복구 워커 호출은 잠금 하나만으로 해결되지 않음을 적는다.

### 3-2. 대안을 비교한다

| 후보 | 장점 | 대가·한계 |
|---|---|---|
| JVM 내부 synchronized | 한 프로세스 구현 간단 | 다른 서버와 조정 불가 |
| 스케줄러 전역 잠금 | 중복 배치 실행 감소 | 잠금 만료·중단·수동 재실행까지 업무 중복을 모두 막지 못함 |
| 청구 UNIQUE + 상태 선점 + 외부 멱등키 | 같은 청구를 여러 경로에서 보호 | 상태 전이·중단 복구·동시성 테스트 필요 |
| 청구 단위 보장 + 스케줄러 잠금 | 업무 중복 방지와 불필요한 작업 감소 | 두 계층 운영 필요 |

- [ ] 기본 선택은 2번의 청구 단위 보장을 완성하는 것으로 둔다. 배치 중복 실행 자체의 비용이 확인되면 전역 잠금을 추가한다.

### 3-3. 변경 전 중복을 재현한다

- [ ] 동일한 만료 구독을 두 실행이 모두 읽은 다음 동시에 처리를 시작하도록 테스트 장벽을 둔다.
- [ ] 결제 테스트 서버에서 서로 다른 주문번호가 만들어지는지와 승인 효과 수를 기록한다.
- [ ] 우연히 두 번째 실행이 이미 연장된 상태를 읽어 중복이 안 난 경우를 동시성 보장으로 해석하지 않는다.

### 3-4. 청구 생성과 실행 선점을 구현한다

1. [ ] 같은 원래 납기의 작업 생성 시 UNIQUE 충돌은 기존 작업 조회로 이어지게 한다. 중복 INSERT 때문에 현재 트랜잭션이 실패 상태라면 별도 정상 트랜잭션에서 조회한다.
2. [ ] 준비 트랜잭션에서 ACTIVE 여부·현재 납기와 전달된 납기 일치·해지 예약을 검증한다. 이미 다른 실행이 연장했다면 건너뛴다.
3. [ ] 한 작업을 조건부 UPDATE 또는 짧은 행 잠금으로 선점한다. 영향 행 수가 1인 실행만 승인 경로로 진입한다.
4. [ ] DB 행 잠금을 외부 승인 대기 내내 유지하지 않는다. 선점 상태를 커밋하고 승인 요청을 보낸다.
5. [ ] 작업자 식별자·버전으로 오래된 작업자가 최신 성공 상태를 거절·실패로 덮어쓰지 못하게 한다.
6. [ ] 선점 기한이 지났다는 이유만으로 새 주문번호를 만들지 않는다. 이전 승인 여부를 먼저 조회하고 같은 청구 식별자를 유지한다.
7. [ ] 성공 확정도 잠금 또는 상태 조건으로 보호한다. 두 복구 실행이 동시에 성공을 반영해도 구독 연장·이력은 한 번이어야 한다.
8. [ ] 결제 준비와 해지 예약이 경합할 때 기준 시점을 정한다. “청구 선점 이전 해지 예약은 이번 청구 제외, 선점 이후에는 진행 중 상태 안내” 같은 정책을 선택하면 해지 코드도 같은 잠금·상태 규칙을 따라야 한다.

### 3-5. 전역 잠금은 필요할 때 추가한다

- [ ] 중복 대상 조회와 배치 실행 비용을 기록하고 전역 잠금이 필요한 이유를 먼저 쓴다.
- [ ] 필요하면 DB 기반 ShedLock 또는 DB 잠금 방식을 비교해 하나만 채택한다. DB named lock을 선택하면 연결 소유·해제 규칙을 해당 MariaDB 버전 문서에서 확인한다.
- [ ] ShedLock을 선택하면 작업 시간에 근거해 `lockAtMostFor`를 정하고 설정 이유를 기록한다. 무한히 긴 잠금으로 실패 복구를 막지 않는다.

### 6-5. 저장 트랜잭션과 커밋 이후 발송을 구현한다

1. [ ] 공지 저장·인앱 알림 생성 중 하나가 실패하면 둘 다 취소할지 정한다. 기본 출발점은 함께 커밋하는 것이다.

3. [ ] 트랜잭션 안에서 공지 ID와 필요한 발송 정보가 담긴 이벤트를 발행한다.

5. [ ] 비동기 작업에 영속성 세션에 의존하는 엔티티를 그대로 넘기지 않고 ID·불변 데이터로 전달한다.

7. [ ] 큐 거절·발송 실패를 Notice 상태에서 확인할 수 있게 한다. 이미 커밋된 공지를 API 오류만으로 “저장 실패”처럼 보이게 하지 않는다.

트랜잭션 이벤트는 기본적으로 실제 트랜잭션에 연결된다. AFTER_COMMIT은 영속 작업 큐가 아니므로 그 자체로 프로세스 중단 복구를 제공하지 않는다. [Spring 트랜잭션 이벤트](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

| SMTP 응답 지연 | API 반환과 발송 완료 시점 분리 |
| 수신자 한 명 실패 | 나머지 처리 유지, 실패 상태·합계 일치 |
| 큐 포화 | 작업 거절 관측 가능, 영구 SENDING으로 방치하지 않음 |
| 일반 공지·수신자 0명 | 메일 없이 올바른 완료 상태 |
| DB 작업 저장 뒤 프로세스 종료 | outbox 선택 시 재시작 후 남은 작업 처리 |
| SMTP 성공 뒤 상태 저장 실패 | 정한 중복 허용 또는 수동 확인 정책 적용 |

- [ ] 작업 기록에 요청 응답 시간과 발송 완료 시간을 각각 적는다.
- [ ] “응답 지연 제거”, “모든 메일 병렬 전송”, “정확히 한 번 발송”처럼 검증 범위를 넘는 문장을 제거한다.

**완료 조건:** 비동기 실행 위치·커밋 순서·실패 처리 범위를 실제 결과로 설명한다. outbox를 선택했다면 재기동 복구까지 확인한다.

## 7. 요청이 몰릴 때 어느 지점부터 느려지고, 개선 후 얼마나 달라질까?

이 절은 실제 k6 부하 테스트 계획이다. 현재는 계획을 작성한 단계이며, 스크립트 구현·환경 기동·부하 발생·결과 측정은 아직 하지 않았다. 녹취의 성능 측정 권고를 실행하는 단계로 포함한다.

### 7-1. 테스트 대상을 아래 순서로 정한다

| 순서 | 대상 | 확인할 질문 | 외부 호출 처리 |
|---|---|---|---|
| 1 | 관리자 사용량 조회 `GET /api/admin/ai-usage` | 로그 규모와 동시 요청 증가에 따라 지연이 어떻게 변하는가? | 공급자 조회 API는 호출하지 않음 |
| 2 | 게스트 리뷰 `POST /api/guest/local-review` | AI 대기 중 요청이 쌓이면 앱 자원이 어디서 부족해지는가? 한도 거절 경로는 어떻게 버티는가? | AI를 고정 응답·지연의 테스트 서버로 대체 |
| 3 | 정기 결제 배치 | 대상 건수 증가 시 완료 시간·DB 자원·실패 복구가 어떻게 변하는가? | 결제사 테스트 더블 사용, HTTP RPS 대신 배치 처리량 측정 |
| 4 | 공지 메일 | 요청 응답·큐 대기·전체 발송 완료 시간이 어떻게 변하는가? | SMTP 테스트 더블 사용, 메일 사례 선택 시 수행 |

- [ ] 1번과 2번을 기본 부하 테스트로 진행한다. 3번은 결제 사례의 규모별 처리 측정으로 추가하고, 4번은 메일 작업을 선택했을 때 수행한다.
- [ ] 관리자 통계는 일반 사용자 요청처럼 높은 실사용 트래픽이 있다고 가정하지 않는다. 큰 데이터 조회의 비용과 여유 용량을 확인하는 합성 실험이라고 적는다.
- [ ] 처음부터 실제 유료 AI나 결제사를 대량 호출하지 않는다. 테스트 서버의 성능 결과를 실제 AI 공급자까지 포함한 서비스 성능으로 쓰지 않는다.

### 7-2. 변경 전후 환경과 성공 조건을 고정한다

- [ ] 부하 생성기와 대상 애플리케이션을 다른 장비 또는 별도 인스턴스에서 실행한다. 같은 PC에서 시작했다면 자원 경쟁이 있는 로컬 예비 측정으로 표시한다.
- [ ] 애플리케이션·DB·Redis 버전, CPU·메모리, JVM 옵션, 커넥션 풀, 인스턴스 수, 네트워크 경로를 기록한다.
- [ ] 변경 전후 동일한 데이터 스냅샷과 조회 기간을 사용한다. 테스트 중 생성되는 로그와 Redis 키의 초기 상태도 맞춘다.
- [ ] ADMIN 테스트 계정의 인증을 준비하고 단일 요청으로 정상 데이터를 받는지 확인한다. 토큰 만료로 인한 401/403을 성능 오류로 섞지 않는다.
- [ ] 목표 p95·오류율·처리량을 측정 전에 적는다. 근거가 없는 서비스 SLA를 만들지 말고 학습용 목표와 실제 제품 요구를 구분한다.
- [ ] 예상하지 않은 5xx·타임아웃 비율이 10초 이상 5%를 넘으면 해당 단계 중단 후 분석하는 것을 초기 실험 기준으로 둔다. 의도한 한도 거절은 이 오류율에서 분리한다.

### 7-3. k6 스크립트를 기능별로 작성한다

- [ ] 조회용 `admin-usage.js`, 게스트 허용 경로용 `guest-allowed.js`, 거절 경로용 `guest-rejected.js`를 만든다. 파일명은 새로 만들 스크립트의 권장 이름이다.
- [ ] BASE_URL·인증·기간·부하 크기·실행 시간을 외부 설정으로 받게 한다. 인증값을 소스나 측정 결과에 저장하지 않는다.
- [ ] 상태 코드뿐 아니라 응답 본문·필수 필드·정해진 데이터도 검사한다. 빠른 오류 응답을 성공 처리량으로 계산하지 않는다.
- [ ] 시나리오별 태그와 성공/거절별 지연 지표를 둔다. 전체 평균 하나로 비교하지 않는다.
- [ ] k6의 check 실패가 테스트 실패 판정에도 반영되도록 threshold를 설정한다. [k6 threshold 설명](https://grafana.com/docs/k6/latest/using-k6/thresholds/)
- [ ] 실행마다 기준 커밋·실험 조건·지표·원본 결과를 함께 저장한다. k6 출력만으로 DB와 JVM 병목을 판단하지 않는다.

### 7-4. 작은 부하부터 단계적으로 실행한다

아래 숫자는 출발용 실험 조건이며 COGI의 실사용량·허용 한계·달성 결과가 아니다.

| 단계 | 조건 | 수행할 일 |
|---|---|---|
| 정상 동작 확인 | VU 1명, 30초 | 인증·본문·외부 호출 대체 확인 |
| 워밍업 | 낮은 부하, 1분 | 캐시·연결 준비. 이후 측정 구간과 분리 |
| 기본 비교 | VU 5명·10명·20명, 각 조건 2분 | 조건별 별도 결과 저장 |
| 한계 탐색 | 직전 단계가 안정적일 때만 부하 증가 | 목표 초과·오류·자원 포화가 시작되는 구간 기록 |
| 변경 후 비교 | 같은 데이터·부하·시간·대기 규칙 | 변경 전과 동일 조건으로 수행 |

- [ ] VU는 가상 사용자 수이며 요청/초와 같지 않다고 기록한다. 각 반복의 대기 시간을 고정하고 비교 중 바꾸지 않는다.
- [ ] 부하 수준을 바꿀 때 이전 요청·큐가 정리됐는지 확인하고 동일하게 워밍업한다.
- [ ] 같은 목표 요청률에서 비교하려면 arrival-rate 시나리오를 추가한다. 반복 한 번에 요청 하나인 경우에만 반복/초와 요청/초가 직접 대응한다. [k6 API 부하 테스트](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)
- [ ] 부하 생성기의 CPU·네트워크와 dropped_iterations도 확인한다. 생성기가 목표 부하를 못 만든 결과를 서버의 처리 한계로 단정하지 않는다. [k6 지표 정의](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)
- [ ] 핵심 비교 조건은 3회 반복하고 각 실행값과 변동을 남긴다. 가장 좋은 값만 고르거나 실행별 p95를 단순 평균해 전체 p95라고 부르지 않는다.

### 7-5. 관리자 통계의 변경 전후를 비교한다

- [ ] 5번에서 만든 로그 1천·1만·10만 건 데이터와 고정 조회 기간을 사용한다.
- [ ] 먼저 같은 데이터에서 부하만 바꾸고, 다음에 같은 부하에서 데이터 규모만 바꾼다. 두 변수를 동시에 바꾸지 않는다.
- [ ] 변경 전에는 현재 전체 조회를, 변경 후에는 첫 페이지·요약·그래프 등 **화면을 완성하는 데 필요한 요청 묶음 전체**를 측정한다.
- [ ] 분리된 API 각각의 지연 외에 화면 데이터 준비 완료 시간·총 응답 바이트 수·총 DB 작업도 기록한다. 페이지 하나만 빨라진 결과를 전체 화면 개선으로 쓰지 않는다.
- [ ] 여러 API로 나뉘면 HTTP 요청/초와 화면 조회 완료/초를 구분한다.
- [ ] 응답 정확성, p50·p95·p99, 성공 처리량, 오류율, 응답 크기, DB CPU·실행 쿼리·커넥션 대기를 비교한다.
- [ ] SQL 상세 로그로 병목을 확인하는 실행과 지연을 측정하는 실행을 구분한다. 전후의 로깅 설정은 같게 유지한다.

### 7-6. 게스트는 허용 경로와 거절 경로를 분리한다

- [ ] 허용 경로는 같은 코드 길이·모델 결과·AI 지연을 사용한다. 지연 0ms와 500ms를 별도 실험으로 시작하고 필요하면 더 긴 대기 조건을 추가한다. 이 값은 실제 모델 지연을 측정한 값이 아니다.
- [ ] 각 테스트 브라우저는 서버가 발급한 토큰으로 최대 3회 사용하도록 준비한다. 계속 성공 경로를 측정할 때는 새 테스트 세션을 공급하고 그 비율을 기록한다.
- [ ] 거절 경로는 한도를 이미 소진한 토큰을 준비한 후 요청한다. 수정 전 403과 수정 후 429를 해당 버전의 기대 응답으로 검사한다.
- [ ] 허용 요청의 지연과 거절 요청의 지연을 별도로 측정한다. 동일 토큰만 반복해 대부분 거절된 결과를 AI 리뷰 처리량으로 쓰지 않는다.
- [ ] 수정 후 거절 응답의 Retry-After를 확인하고 거절 요청 때문에 AI 테스트 서버 호출 수가 증가하지 않는지 검사한다.
- [ ] Redis 오류율·응답 지연·메모리와 앱 CPU·메모리·GC·요청 대기 상태를 함께 본다.
- [ ] AI 응답 고정 조건은 COGI 애플리케이션의 동작을 비교하는 데 사용한다. 실제 AI 호출은 별도의 소량 종단간 확인으로 구분한다.

### 7-7. 병목 하나를 바꾸고 같은 실험을 반복한다

- [ ] p95가 나빠진 구간에서 DB 쿼리, 커넥션 대기, AI 대기, JVM 자원, Redis 지연 중 증거가 있는 원인을 찾는다.
- [ ] 인덱스·조회 구조·풀 크기를 한꺼번에 바꾸지 않고 한 변경의 영향을 비교한다.
- [ ] 개선 후에도 응답 본문과 정합성 테스트가 유지되는지 확인한다.
- [ ] 처리량 증가 대신 DB 부하·메모리·구현 복잡도가 증가했다면 그 대가를 적는다.
- [ ] 유의미한 차이가 없거나 더 느려졌으면 그대로 기록하고 선택을 재검토한다.

### 7-8. 결과표와 완료 기준을 남긴다

| 조건 | 변경 전 | 변경 후 |
|---|---|---|
| 커밋·환경·데이터·부하·시간 | 실행 후 기록 | 동일 조건 여부 확인 |
| 성공 작업/초 및 HTTP 요청/초 | 미측정 | 미측정 |
| 성공 경로 p50·p95·p99 | 미측정 | 미측정 |
| 예상하지 않은 오류율·타임아웃 | 미측정 | 미측정 |
| 의도한 한도 거절 수·거절 경로 지연 | 미측정 | 미측정 |
| DB·Redis·JVM 주요 자원 | 미측정 | 미측정 |
| 원본 결과·서버 지표·테스트 스크립트 | 실행 후 연결 | 실행 후 연결 |

**완료 조건:** 동일 조건에서 변경 전후의 부하 테스트를 실제 실행하고, 성공 응답의 지연·처리량·오류율과 서버 지표를 함께 해석한다. 목표 달성 여부와 남은 병목을 기록한 뒤 포트폴리오에 반영한다.

## 8. 각 작업을 포트폴리오로 마무리하는 절차

### 8-1. 소제목별로 아래 기록을 작성한다

| 작성 순서 | 써야 하는 내용 | 스스로 확인할 질문 |
|---|---|---|
| 1. 문제 | 어떤 입력·상태에서 무엇이 잘못됐는지 | 운영 경험인가, 테스트 재현인가? |
| 2. 제약 | 기간·인프라·정확성·복구 요구 | 내가 확인한 조건인가? |
| 3. 후보 | 같은 요구를 해결하는 2~3개 대안 | 탈락 후보를 일부러 불리하게 적지 않았나? |
| 4. 선택 | 내 조건에서 선택한 구체적인 이유 | 유행·막연한 성능 말고 이유가 있는가? |
| 5. 대가 | 선택 때문에 늘어난 비용·포기한 보장 | 장점만 적지 않았나? |
| 6. 구현 | 실제 변경한 클래스·메서드·상태·경계 | 설명과 현재 코드가 일치하는가? |
| 7. 검증 결과 | 조건·실제 결과·증거 위치 | 수치와 결과를 재현할 수 있는가? |
| 8. 남은 한계 | 미구현·미검증·범위 밖 보장 | 계획을 성과로 쓰지 않았나? |

- [ ] 작업 전 선택 이유를 먼저 적고, 작업 후 실제 결과를 추가한다.
- [ ] 피드백을 받은 뒤 조사한 대안은 “리팩토링에서 재검토”라고 쓴다.
- [ ] 실패한 실험도 선택 이유를 설명하는 근거이면 남긴다. 모든 시도가 개선될 필요는 없다.

### 8-2. 증거 묶음을 만든다

- [ ] 변경 전·후 커밋을 기록한다. 기존 주석 추가를 기능 변경 성과로 쓰지 않는다.
- [ ] 테스트 클래스와 실제 실행 명령을 적는다.
- [ ] 테스트 환경·데이터 생성 방법·실행 시각을 적는다.
- [ ] DB 최종 상태, Redis TTL, HTTP 응답, 외부 승인 효과 등 사례에 맞는 원본 증거를 보관한다.
- [ ] 성능 결과는 환경·데이터·워밍업·반복 횟수·오류율을 같이 적는다.
- [ ] 로그에서 토큰·결제 키·실사용자 개인정보를 제외한다.
- [ ] 재현 명령을 새 테스트 데이터에서 다시 실행해 같은 결론이 나오는지 확인한다.

### 8-3. 최종 포트폴리오 소제목을 고른다

아래는 작업을 완료했을 때 사용할 수 있는 제목 후보다. 아직 확인하지 않은 결과는 본문에 넣지 않는다.

| 실제 완료한 작업 | 포트폴리오 제목 후보 |
|---|---|
| 1번만 완료 | 정기 결제 배치의 트랜잭션 경계를 어디에 둘까? |
| 1~3번 완료 | 정기 결제의 실패 격리와 중복 승인 방지를 어떻게 함께 보장할까? |
| 4번 완료 | 비로그인 체험 한도를 Redis에 맡길 때 무엇까지 보장할까? |
| 5번 완료 | 관리자 통계에서 목록 조회와 전체 집계를 분리할까? |
| 6번 기본 범위 완료 | 공지 저장과 메일 발송의 실행 시점을 어떻게 나눌까? |
| 6번 outbox까지 완료 | 공지 메일의 응답 속도와 재기동 복구를 어떻게 함께 확보할까? |

- [ ] 대표 사례는 결제·게스트부터 고른다. 통계·메일은 증거가 있는 사례를 추가한다.
- [ ] 이력서에는 문제·핵심 선택·검증 결과를 짧게 쓰고, 포트폴리오에는 비교·대가·실패 경계까지 설명한다.
- [ ] 기록할 숫자가 없으면 재현 가능한 상태 변화로 결과를 쓴다. 예: 승인 응답 유실 후 조회로 복구했고 추가 승인 없이 구독이 한 번 연장됨. 이 문장도 해당 테스트를 통과한 뒤 사용한다.

## 9. 작업 완료 체크와 커밋 단위

| 작업 묶음 | 끝내고 넘어갈 조건 | 권장 커밋 주제 |
|---|---|---|
| 공통 준비 | 테스트 자원 분리·외부 호출 대체·기준 결과 확보 | 테스트 환경 분리 |
| 결제 격리 | A/B/C DB 커밋·롤백 검증 | 결제 격리 테스트와 오류 관측 |
| 결제 복구 | 불명 결과 추적·승인 조회·로컬 반영 복구 | 청구 작업 상태와 복구 |
| 결제 동시성 | 두 프로세스·재실행에서도 승인 효과·연장 중복 없음 | 청구 선점과 중복 처리 방지 |
| 게스트 제한 | 동시 요청·만료·반환 검증, 429/503 화면 연결 | 체험 한도 원자성 및 오류 계약 |
| 통계 조회 | 목록·합계 정확성 유지, 동일 조건 측정 완료 | 목록 페이징·집계 분리 |
| 공지 메일 | 선택한 신뢰성 수준의 테스트 통과 | 커밋 이후 발송 및 선택한 복구 방식 |
| 부하 테스트 | 조회·게스트 변경 전후 동일 조건 실행, 지연·성공 처리량·오류·서버 지표 비교 | k6 시나리오와 부하 테스트 결과 |
| 포트폴리오 | 구현·결과·한계와 증거 연결 | 사례별 실험 기록 |

변경 묶음마다 관련 테스트와 필요한 프론트 빌드를 실행한다. 스키마·결제 계약처럼 영향이 큰 변경 뒤에는 관련 회귀 테스트를 함께 실행한다. 문서 체크만 끝난 상태와 구현·검증까지 끝난 상태를 혼동하지 않는다.
