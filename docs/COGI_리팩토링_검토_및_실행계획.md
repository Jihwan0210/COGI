## 1. 판정: 작성 방향은 맞지만 그대로 구현 계획으로 쓰면 안 된다

`제약 → 대안 비교 → 선택 이유 → 감수한 비용 → 구현 → 검증 결과 → 남은 한계`는 좋은 골격이다. 다만 현재 문서에는 **멘토 발언, 작성자의 해석, 이미 구현한 사실, 새로 할 일, 예시 수치**가 섞여 있다.

녹취에서 반복된 핵심은 “기술을 더 많이 도입하라”가 아니라 **문제와 판단 과정을 설명하고 실행 결과로 입증하라**는 것이다. 각 사례에 무엇을 결정해야 했는지, 왜 그 선택을 했는지, 실제로 어디까지 확인했는지가 있어야 한다.

## 3. 권장 순서와 완료 기준

진행 순서: **기준선 확보 → 결제 격리 검증 → 결제 복구·중복 방지 → 게스트 한도 → 통계 조회 → 공지 메일 선택 개선 → 포트폴리오 정리**.

우선 결제와 게스트 두 사례를 끝낸다. 통계와 메일은 실제 측정·재현 결과를 보고 세 번째 사례로 선택한다. Kafka, Sentinel, Spring Batch 도입을 완료 조건으로 삼지 않는다.

### 0단계. 수정 전 상태와 테스트 환경을 확보한다

- [ ] 기존 미커밋 변경을 검토해 기준 커밋 또는 별도 패치로 보관한다. 다른 작업의 변경과 섞지 않는다.
- [ ] Spring Boot 4.1.0 / Java 25라는 선언과 실제 로컬 JDK·DB·Redis 버전을 기록한다. DB 드라이버와 JDBC URL은 MariaDB이므로 MySQL이라고 뭉뚱그리지 않는다.
- [ ] 테스트 전용 DB·Redis와 프로필을 만든다. 현재 application.properties:20은 `ddl-auto=create`이므로 기존 데이터를 사용하는 기본 설정으로 통합 테스트를 기동하지 않는다.
- [ ] 실제 결제·AI·SMTP는 테스트 더블로 바꾼다. 결제 API 계약 확인은 별도의 결제사 테스트 환경에서 한다.
- [ ] SQL 수, API 응답 시간, 외부 승인 시도 수, DB 최종 상태를 각각 수집할 방법을 정한다.
- [ ] 결제 배치, 게스트 한도, 사용량 조회, 공지 발송의 직접 검증 테스트를 추가할 위치를 정한다. 현재 테스트 목록에서는 이 네 경로의 전용 테스트를 확인하지 못했다.

완료 기준: 같은 입력으로 수정 전 동작을 다시 재현할 수 있고, 어떤 결과를 측정할지 정해져 있다. 과거 장애가 이미 고쳐져 있으면 Git 이력의 실제 변경 전 코드를 찾는다. 찾지 못하면 “새로 구성한 재현 실험”이라고 표기한다.

### 1단계. 이미 있는 결제 실패 격리를 먼저 증명한다

- [x] BillingScheduler → 별도 BillingProcessor 빈 호출 구조 확인.
- [x] 건별 성공·실패 처리 메서드의 기본 @Transactional 확인.
- [ ] Spring 컨텍스트와 실제 테스트 DB로 구독 A/B/C를 준비한다. B만 결제 거절하도록 결제 클라이언트를 대체한다.
- [ ] 배치 후 A/C의 연장·이력이 커밋됐는지, B는 현재 정책대로 강등됐는지 새 트랜잭션에서 조회한다.
- [ ] B 실패 후 C도 실행됐는지 확인한다. 단순 Mockito 호출 횟수만으로 DB 커밋·롤백을 증명하지 않는다.
- [ ] 주석 처리된 실패 로그를 복구하고 구독 ID·청구 작업 ID·예외 종류를 남긴다. 결제 비밀키는 기록하지 않는다.
- [ ] 문서를 “외부 트랜잭션 없는 스케줄러 + 별도 빈의 REQUIRED로 건별 처리”로 고친다.

현재 구조에 REQUIRES_NEW를 추가하는 것은 필수가 아니다. 외부 트랜잭션이 생겨도 격리해야 한다는 요구가 있으면 그때 비교한다. REQUIRES_NEW는 새 스레드가 아니며, 외부 트랜잭션을 유지하면서 추가 커넥션을 사용할 수 있다. [Spring 전파 옵션](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

완료 기준: “B의 실패가 A/C의 DB 변경을 되돌리지 않는다”를 실행 결과로 설명할 수 있다. 이것만으로 결제사 승인까지 원자적으로 롤백된다고 쓰면 안 된다.

### 2단계. 결제 복구 기반을 만든 뒤 재시도를 붙인다

지금 더 중요한 위험은 **결제사 승인 성공 → DB 저장·커밋 실패 → 스케줄러가 결제 실패로 간주해 강등**하는 경로다. 로컬 DB 트랜잭션은 이미 완료된 외부 승인을 취소하지 않는다. 최초 구독·업그레이드도 같은 형태를 쓰므로 정기 결제 개선 후 같은 원칙을 적용할 대상으로 남긴다.

- [ ] 먼저 정책을 구분한다: 확정 거절 / 결과 불명(타임아웃 등) / 승인 확인 후 DB 반영 실패 / 운영 오류.
- [ ] “3회”를 확정값으로 두지 말고 재시도 가능 오류, 간격, 상한, 유예기간, 최종 강등 조건을 정한다. 결과 불명 상태는 조회·대사 대상으로 둔다.
- [ ] 청구 의도를 저장할 BillingJob/BillingAttempt 등의 저장소를 설계한다. 이름은 예시다. 최소 정보는 구독 ID, 청구 주기, 금액, orderId, 멱등키, 상태, 시도 횟수, 다음 실행 시각, 오류 정보, paymentKey다.
- [ ] 청구 주기 키는 “실행한 현재 월” 대신 원래 납기·청구 대상 기간으로 정의한다. 날짜가 바뀌어 재실행돼도 같은 청구는 같은 키를 사용한다. 업그레이드 차액 청구와 갱신 청구도 구분한다.
- [ ] DB UNIQUE와 조건부 상태 갱신 또는 잠금으로 동일 청구 작업을 선점한다. 실제 청구 직전에 ACTIVE·납기·해지 예약을 재검증한다.
- [ ] 짧은 DB 트랜잭션으로 PENDING 및 요청 식별자를 **커밋한 뒤** 외부 승인 요청을 보낸다. 대기 중 장시간 DB 트랜잭션을 잡는 범위를 줄인다.
- [ ] 같은 승인 시도의 재전송은 저장된 orderId·멱등키·금액을 재사용한다. 명확히 종료된 시도 이후 새 결제 시도를 허용하는 조건은 별도로 정한다.
- [ ] 응답의 결제 상태·금액·orderId를 확인하고 paymentKey를 보관한다. SUCCESS 확정과 구독 연장·갱신 이력 반영은 같은 DB 트랜잭션으로 처리한다.
- [ ] 타임아웃·프로세스 중단·승인 후 DB 장애는 저장된 주문 식별자로 결제사 상태를 조회하고 대사한다. 한 번의 “조회 결과 없음”을 즉시 미승인 확정으로 취급하지 않도록 조회 지연 정책도 둔다.
- [ ] 이미 SUCCESS인 작업을 다시 처리해도 재승인·재연장되지 않게 한다. 재처리 워커도 동일한 선점 규칙을 따른다.
- [ ] 그다음 실패 작업을 읽는 재처리 경로를 붙인다. 확인 불가 상태는 자동 강등보다 수동 확인 대상으로 남길 수 있다.
- [ ] 승인 완료 메일은 로컬 성공 커밋 이후로 옮긴다. 복구 후에도 알림이 필요하면 영속 발송 작업을 남긴다.
- [ ] 애플리케이션 2개에서 동시 실행을 재현한다. 스케줄러 잠금이 필요하면 DB 기반 잠금과 ShedLock 중 하나를 선택하고 시간 초과·프로세스 중단을 테스트한다. 잠금만으로 중복 승인을 막았다고 결론 내리지 않는다.

토스는 POST 요청의 `Idempotency-Key`와 주문 ID 결제 조회를 문서화한다. 키 유효기간·처리 중 응답·오류 재전송 규칙을 적용 시 확인한다. DB의 UNIQUE는 외부 API의 멱등성을 대신하지 않는다. [멱등키 규칙](https://docs.tosspayments.com/reference/using-api/authorization), [결제 조회·자동결제 API](https://docs.tosspayments.com/reference)

검증할 시나리오:

| 입력·장애 | 통과 조건 |
|---|---|
| A/B/C 중 B 거절 | A/C 성공 유지, B만 선택한 실패 정책 적용 |
| 동일 청구 동시 실행 | DB에 하나의 청구 의도, 외부 승인 효과 1회, 연장 1회 |
| 승인 성공 뒤 응답 유실 | 즉시 FREE 강등 없이 조회·대사로 상태 확정 |
| 승인 성공 뒤 DB 반영 실패 | 재기동 후 승인 내역을 찾아 DB 반영, 추가 승인 없음 |
| PENDING 커밋 뒤 프로세스 종료 | 남은 작업 발견·복구 가능 |
| SUCCESS 작업 재처리 | 승인·이력·연장 중복 없음 |
| 해지 예약 또는 다른 실행이 이미 연장 | 최신 상태 확인 후 잘못된 추가 청구 없음 |

테스트 더블의 승인 효과 1회와 실제 결제사 테스트 결과를 구분해 기록한다. 결제 배치 통합 테스트에 외부 테스트 트랜잭션을 씌우면 실제 경계가 달라질 수 있으므로 실제 호출 구조를 유지한다.

### 3단계. 게스트 한도를 하나의 일관된 정책으로 만든다

- [ ] 정책을 “동일 토큰, 첫 허용 요청부터 24시간, 최대 3개 체험 사용권”처럼 정의한다. 자정 초기화와 섞지 않는다.
- [ ] 폴백까지 포함한 체험 1회와 실제 AI 공급자 호출 횟수를 구분한다. 체험 3회가 외부 API 호출 3회를 보장하는 것은 아니다.
- [ ] DB 카운터의 원자적 조건부 갱신 + 만료 시각 방식과 Redis 방식을 같은 정책으로 비교한다. 저장 용량·원격 접근·장애 의존·구현 복잡도·기존 활용처를 적는다.
- [ ] 기존 Redis에는 체험 결과도 저장한다는 사실을 판단 근거에 포함한다. 성능 우위를 측정하지 않았다면 “이미 쓰는 저장소와 만료 정책을 재사용했다” 수준으로 설명한다.
- [ ] 제한 판단·증가·최초 만료 설정·남은 TTL 반환을 짧은 Lua 스크립트 등으로 원자화한다. 거절된 요청을 계속 증가시킬 필요도 검토한다.
- [ ] Redis 명령 결과가 null이거나 장애가 발생하면 1회로 간주하지 않는다. 제한을 확인할 수 없을 때 AI 호출을 중단하고 명시적으로 503을 반환하는 정책을 구현한다.
- [x] 모든 폴백 실패 시 DECR 코드가 존재함을 확인.
- [ ] 사용권 반환은 요청·윈도 식별자를 기준으로 중복되지 않게 한다. 만료된 키에 DECR해 음수 키를 만들거나 다음 윈도 카운터를 깎지 않도록 한다.
- [ ] AI 응답 성공 뒤 Redis 결과 저장 실패도 별도 정책으로 정한다. 이미 비용이 발생했으므로 무조건 무료 재호출로 이어지지 않게 한다.
- [ ] 상한 초과를 429와 실제 남은 TTL 기반 Retry-After로 응답한다. 장애 503과 한도 소진 429를 구분한다. Retry-After는 RFC상 선택 헤더지만 이 서비스에서는 재시점 안내를 위해 넣는다. [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585#section-4)
- [ ] 프론트 GuestReview의 403 분기를 429 정책에 맞춘다. 남은 시간을 표시하면 API 클라이언트의 응답 헤더 전달과 다른 origin의 CORS 헤더 노출도 함께 확인한다.
- [ ] 동일 쿠키로 동시에 여러 요청을 보내 허용된 리뷰 작업이 3개를 넘지 않는지 확인한다. 공급자 폴백 호출 수는 따로 센다.
- [ ] Redis 중단, TTL 만료, 만료 직후 이전 요청 실패, 중복 반환을 재현한다. AI 실패로 사용권을 돌려주는 경우의 기대 결과도 명시한다.
- [ ] 쿠키 삭제·교체와 쿠키 없는 동시 첫 요청의 우회 가능성을 기록한다. Redis 장애 시 다른 기능도 영향 없는지는 실제 의존 경로를 점검해 별도로 검증한다.

완료 기준: 순차·동시 요청에서 정책이 같고, 제한 초과 요청은 AI 실행 전에 거절되며, 실패·만료 경계에서 영구 차단이나 추가 사용권이 생기지 않는다. 총 AI 비용의 상한까지 보장한다고 주장하지 않는다.

### 4단계. 관리자 통계는 현재의 전체 조회 문제부터 측정한다

- [x] 사용자 닉네임 일괄 조회는 이미 구현되어 있음.
- [ ] 과거 N+1 변경 전 커밋이 있는지 찾고 SQL로 확인한다. 현재 코드만 보고 “21회가 2회로 줄었다”고 쓰지 않는다.
- [ ] 사용자 수, 로그 수, 고유 userId 수, 게스트 비중, 조회 기간과 실행 환경을 고정한다. 첫 조회와 캐시가 준비된 조회를 구분한다.
- [ ] 서비스 SQL 수와 인증 등을 포함한 전체 HTTP 요청 SQL 수를 구분한다. “항상 2회” 대신 측정 범위와 조건을 적는다.
- [ ] 현재 API 응답 크기·시간·반환 행 수를 측정한다. 목록뿐 아니라 전체 통계 데이터를 보내는 비용이 얼마나 큰지 확인한다.
- [ ] 서버 페이징을 적용할지 판단한다. 적용 시 목록과 기간 전체 합계·일별 그래프 집계를 분리한다. 페이지 데이터만 프론트에 넘기면 현재 합계·그래프가 일부 데이터만 계산하게 된다.
- [ ] DTO 조인 조회와 페이지 내 ID 일괄 조회를 비교한다. 게스트 userId=null 및 탈퇴한 사용자도 누락시키지 않는다. 조인을 택하면 LEFT JOIN 의미를 검토한다.
- [ ] 필요하면 Page의 전체 count 비용과 Slice/커서 방식의 제약을 비교한다. 쿼리 수가 늘어도 반환량이 크게 줄어 더 나을 수 있다.
- [ ] 테스트 DB의 실제 인덱스를 확인하고 기간 필터·정렬 SQL을 EXPLAIN한다. 엔티티에 인덱스 선언이 없다는 이유만으로 운영 DB에도 없다고 단정하지 않는다.
- [ ] 후보 인덱스를 추가하기 전후로 반환 결과 일치·스캔 행·정렬·응답 시간을 비교한다. 쓰기 비용·저장 공간도 적는다.
- [ ] 지연 개선은 동일 조건으로 반복 측정한다. 부하에서의 p95·처리량을 말하려면 별도의 부하 생성기로 동일 시나리오를 수행한다.

완료 기준: “쿼리 2회”가 아니라 **데이터 증가에 따른 비용과 선택한 조회 방식의 대가**를 설명할 수 있다. 유의미한 개선이나 판단 근거가 없으면 대표 사례에서 제외하고 구현 기록으로 남긴다.

### 5단계. 공지 메일은 선택 사례로 다룬다

- [x] EnableAsync, 프록시 경유, 전용 Executor가 이미 있음.
- [ ] “수신자 모두 병렬 발송” 대신 “요청 스레드에서 분리하고 한 작업 안에서는 순차 발송”으로 설명한다.
- [ ] API 반환 시점과 전체 메일 발송 완료 시점을 별도로 측정한다. 회원 조회와 인앱 알림 생성은 아직 요청 경로에 있으므로 “응답 지연 제거”라고 일반화하지 않는다.
- [ ] 현재 저장 커밋 순서를 테스트하고, 공지·인앱 알림을 하나의 트랜잭션으로 묶을 필요가 있는지 정한다.
- [ ] 묶기로 했다면 트랜잭션 안에서 이벤트를 발행하고 AFTER_COMMIT에서 발송을 위임한다. 현재처럼 외부 트랜잭션이 없는 메서드에 리스너만 추가하면 기본 설정에서는 실행되지 않을 수 있다. [Spring 트랜잭션 이벤트](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)
- [ ] mailExecutor 큐 포화·작업 거절·프로세스 중단을 재현하고 사용자에게 보일 상태를 정한다.
- [ ] 발송 유실 방지가 요구되면 같은 트랜잭션으로 발송 작업을 저장하는 DB outbox 방식을 비교한다. AFTER_COMMIT + Async만으로 재기동 복구가 되지는 않는다.
- [ ] 재시도가 필요하면 수신자별 상태를 저장한다. 현재 성공·실패 합계만으로는 실패한 수신자를 복원하기 어렵다. 일반 SMTP의 전송 후 기록 실패는 중복 메일 가능성이 남는다는 점도 설명한다.

완료 기준: 무엇이 비동기인지, 커밋 이후 무엇을 보장하는지, 실패 작업이 어떻게 남고 복구되는지 설명할 수 있다. 신뢰성 요구가 낮다면 인메모리 방식의 한계를 수용하는 것도 선택이다.

### 6단계. 검증을 끝낸 사례만 포트폴리오 문장으로 바꾼다

- [ ] 문서마다 `[현재 구현]`, `[코드상 위험]`, `[재현 완료]`, `[새 설계]`, `[검증 완료]`, `[남은 과제]`를 구분한다.
- [ ] 당시 선택과 피드백 이후 재검토한 대안을 나눈다. 나중에 조사한 대안을 당시 검토한 것처럼 쓰지 않는다.
- [ ] 수백 건·500명·페이지 20건·320ms 등의 예시를 실제 규모처럼 쓰지 않는다.
- [ ] 테스트 조건·기준 커밋·데이터 생성 방법·실행 명령·SQL/결과 파일 위치를 남긴다.
- [ ] 실제 운영 장애, 테스트에서 발견한 결함, 장애를 가정한 설계 실험을 구분한다.
- [ ] 코드 주석에는 구현 이유와 제약만 짧게 남기고, 자세한 비교·실험 결과는 문서에 둔다. 주석의 “결과”도 검증 없이 확정적으로 쓰지 않는다.

## 4. 실제로 작성할 사례 틀

아래는 결과를 꾸며 넣지 않기 위한 기록 양식이다. 미측정 칸은 검증 후 채운다.

| 항목 | 기록할 내용 |
|---|---|
| 결정 질문 | 예: 정기 결제의 승인 결과가 불확실하면 재청구할 것인가, 먼저 조회할 것인가? |
| 발견 경로 | 운영/로컬 테스트/장애 주입 실험 중 무엇인지 |
| 제약과 보장 범위 | 인스턴스 수, 저장소, 결제사 API, 같은 청구를 식별하는 기준 |
| 같은 문제를 푸는 대안 | 각 대안의 장점, 적용 비용, 실패 시 동작 |
| 선택 이유 | 현재 규모·인프라·정합성 요구와 연결 |
| 감수한 대가 | 테이블·상태 전이·외부 조회·운영 복잡도 등 실제 추가 비용 |
| 구현 근거 | 실제 클래스·메서드·커밋 |
| 검증 | 입력 조건, 장애 주입 지점, 기대 결과, 실제 결과, 증거 파일 |
| 미해결 범위 | 승인 조회 불가, 외부 API 보장 기간, 수동 처리 필요 조건 등 |

수치가 없어도 “B를 실패시킨 뒤 별도 트랜잭션에서 조회했을 때 A/C 연장 이력은 남았다”는 재현 가능한 결과다. 반대로 측정하지 않은 “안정성 향상”, “성능 70% 개선”은 근거가 아니다.

## 5. 첫 작업 묶음

지금 당장 시작할 일은 아래 네 가지다. 한 번에 모든 구조를 바꾸지 않는다.

1. 기준 변경을 보관하고 테스트 프로필·전용 DB를 준비한다.
2. BillingScheduler의 A/B/C 실패 격리 통합 테스트를 만든다.
3. 승인 성공 후 DB 반영 실패를 주입해 현재 강등 경로를 재현한다.
4. 결과를 보고 청구 작업 상태표와 오류별 정책을 먼저 작성한다.

그 후 2단계의 복구 기반을 구현한다. 이 순서이면 이미 있는 기능을 다시 만들지 않고, 발견 → 선택 → 구현 → 검증의 연결을 남길 수 있다.

검토 범위: 소스·문서·기존 변경 내용 및 관련 공식 문서 확인. 애플리케이션 기동, 결제 호출, DB 변경, 테스트 실행, 성능 측정은 수행하지 않았다. 이 문서는 리팩토링 완료 보고서가 아니라 실행 계획이다.
