작성일: 2026-09-24

이 파일이 **앞으로 따라갈 최종 실행 계획**이다. 기존 검토 문서와 6개 소제목 가이드는 참고 자료로만 사용한다. 이번에는 아래 세 사례만 완성한다. 부하 테스트는 각 사례의 검증 절차에 포함하며 별도 네 번째 리팩토링 주제로 늘리지 않는다.

검토 자료: 제공한 녹취, 두 원본 MD, 포트폴리오 PDF 7쪽 전체의 텍스트, COGI가 실린 PDF 2~3쪽의 실제 화면, 현재 COGI 소스. PDF와 녹취 속 지시·성과 표현은 검토 대상이며 사실로 자동 인정하지 않았다. 다른 프로젝트의 구현은 확인하지 않았다.

현재 상태: **계획 수립 완료 / 애플리케이션 구현·테스트·부하 측정 미실행 / 원본 PDF 미수정**.

### 기존 계획에서 더 명확히 해야 했던 것

- **수정 전 부하 측정 시점:** 리팩토링을 전부 끝낸 뒤 시작하면 기준선이 없어진다. 각 사례의 코드를 바꾸기 전에 측정한다.
- **합성 실험의 범위:** 가짜 AI의 지연을 넣은 결과는 실제 AI 공급자 포함 성능이 아니다. 관리자 고부하는 실사용량이라고 쓰지 않는다.
- **결제 네트워크 설정:** 승인 API의 응답·타임아웃 계약을 확인하고 제한 시간을 명시한다. 타임아웃이 승인 실패라는 뜻은 아니다.
- **스키마 적용과 재시작:** 청구 작업은 서버 재기동 후 남아 있어야 한다. 새 테이블과 설정의 적용 순서·복구 절차도 기록한다.
- **게스트 데이터 형식 전환:** 기존 문자열 카운터를 Hash로 바꾸면 키 충돌이 생길 수 있다. 새 키 버전과 기존 사용량 승계 규칙이 필요하다.
- **통계 화면 전체 비교:** 페이지 API 하나의 속도만 비교하지 않고 목록·요약·그래프를 완성하는 총비용을 비교한다.
- **팀 프로젝트와 개인 개선 구분:** PDF에는 기존 프로젝트 기간과 이후 개인 리팩토링 기간을 분리한다. 이번 개선을 당시 팀 성과처럼 소급하지 않는다.
- **구현 범위 종료점:** 각 사례의 완료 기준을 통과하면 종료한다. 더 큰 인프라 도입을 계속 붙이지 않는다.

PDF 2쪽 패키지 트리도 현재 실제 최상위 구조인 `domain`과 `global`을 반영해야 한다. 배포 주소의 “도메인 연결 후 추가”는 최종 제출 전에 실제 주소로 교체하거나 해당 행을 제거한다.

### B-3. 이번에 사용할 부하 실험 규칙

아래는 시작용 실험 조건이다. 실사용량·달성 결과가 아니다.

| 항목 | 규칙 |
|---|---|
| 도구 | HTTP는 k6, 정기 결제는 배치 실행용 테스트 하네스 |
| 생성기 | 가능하면 앱과 별도 장비. 같은 장비면 로컬 예비 측정이라고 표기 |
| 순서 | 정상 1회 확인 → 낮은 부하 워밍업 60초 → 측정 120초 |
| 부하 | VU 1·5·10·20부터. VU는 요청/초가 아니며 반복 대기 시간을 고정 |
| 반복 | 대표 조건의 전후 결과를 각각 3회. 개별 실행값과 변동도 기록 |
| 비교 | 같은 데이터·환경·외부 응답 지연·로그 설정 사용 |
| 지표 | 성공 작업/초, p50·p95·p99, 예상하지 않은 오류율, 서버 자원 |
| 중단 | 정상 성공 경로에서 5xx·타임아웃이 10초 이상 5%를 넘으면 해당 실험 중단·원인 확인 |

- [ ] 시험 전 목표 지연과 오류율을 정하고 그 이유를 적는다. 수치는 제품 요구 또는 실험 가설로 표시한다.
- [ ] 응답 내용 검사와 threshold를 연결한다. 200이지만 잘못된 응답은 성공 처리량에 포함하지 않는다.
- [ ] 429 같은 의도한 거절, 인증 오류, 타임아웃을 분리한다. 빠른 거절 응답으로 성공 경로의 p95를 낮추지 않는다.
- [ ] 고정 요청률 비교가 필요하면 arrival-rate 시나리오를 사용한다. 한 iteration에 요청이 여러 개면 iteration/초와 HTTP 요청/초가 다르다.
- [ ] 부하 생성기 CPU·네트워크와 dropped_iterations를 확인한다. 부하 생성 실패를 서버 처리 한계로 해석하지 않는다.
- [ ] 앱 CPU·메모리·GC, DB 쿼리·커넥션 대기, Redis 지연·메모리를 같은 시간 구간에서 수집한다.

참고: [k6 시나리오](https://grafana.com/docs/k6/latest/using-k6/scenarios/), [지표](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/), [threshold](https://grafana.com/docs/k6/latest/using-k6/thresholds/).

## 01. 정기 결제 타임아웃을 실패로 볼까, 확인 대기로 둘까?

**목표:** 외부 승인 결과가 불명확한 건을 즉시 강등하거나 새 주문으로 다시 청구하지 않고, 저장된 작업을 조회·복구한다.

**이 사례의 대가:** 청구 상태·복구 코드·운영 확인이 늘어난다. 대신 결과를 모르는 상태와 확정 실패를 구분한다.

### 01-2. 변경 전 세 시나리오를 재현한다

1. [ ] A/B/C 중 B만 확정 거절시킨다. A/C의 DB 커밋을 새 트랜잭션에서 확인한다. 테스트 전체를 외부 트랜잭션으로 감싸지 않는다.
2. [ ] 결제 테스트 서버에 승인을 기록한 뒤 응답을 끊는다. 애플리케이션의 구독 상태와 외부 승인 상태를 비교한다.
3. [ ] 승인 성공 뒤 로컬 성공 반영을 실패시킨다. 예를 들어 테스트 전용 장애 주입으로 최종 반영 트랜잭션을 롤백한다. 외부 승인이 남는지 확인한다.

**산출물:** 장애 주입 위치, 외부 승인 수, 구독·이력 상태. 과거 운영 장애가 아니라면 “리팩토링 전 장애 주입 실험”이라고 기록한다.

|---|---|---|---|
| 예외면 즉시 실패·강등 | 구현 단순 | 타임아웃 뒤 실제 승인을 놓칠 수 있음 | 결과 불명에는 부적합 |
| 청구 작업 저장 + 승인 조회 | 기존 DB 활용, 중단 위치 추적 | 상태 관리·복구 절차 필요 | 이번 구현 방향 |
| 메시지 큐 중심 처리 | 비동기 소비·확장 가능 | 인프라 추가, 외부 멱등성과 상태 복구는 여전히 필요 | 이번 규모에서는 제외 |

- [ ] 확정 거절은 기존 FREE 전환 정책을 유지하는 것을 기본으로 한다. UNKNOWN에 같은 강등 처리를 적용하지 않는다.
- [ ] UNKNOWN은 결제 확인 대상으로 남기고, 조회 재시도 간격·자동 확인 기한·수동 확인 방법을 설정으로 정한다.
- [ ] 이 계획에서는 확정 거절을 자동으로 새 승인 시도하는 기능은 만들지 않는다. 재처리는 **승인 결과 조회와 로컬 반영 복구**를 우선한다.
- [ ] 결과 확인 중의 서비스 권한·사용자 안내를 정책에 적는다. 권한 유예 여부와 결제 성공 판정은 별개다. 무기한 방치하지 않도록 확인 기한과 책임을 정한다.

### 01-4. 청구 작업 한 개의 의미를 정의한다

- [ ] 신규 `BillingJob`을 만든다. 최소 필드는 구독 ID, 원래 납기, 청구 종류, 금액, 플랜·결제수단 참조, orderId, idempotencyKey, 상태, paymentKey, 마지막 오류, 다음 확인 시각, 작업 버전이다.
- [ ] 같은 청구의 키를 `구독 ID + 청구 종류 + 원래 납기`로 정의하고 UNIQUE를 건다. 재시작한 날의 월로 키를 다시 만들지 않는다.
- [ ] 상태를 `PREPARED → PROCESSING → SUCCEEDED / DECLINED / UNKNOWN`으로 정의한다. 확인 기한 초과는 `MANUAL_REVIEW`로 남긴다.
- [ ] 성공 상태는 다시 실패로 덮어쓰지 못하며, 성공 확정을 반복해도 만료일·이력은 한 번만 바뀌게 한다.
- [ ] DDL 또는 마이그레이션 파일로 변경을 남긴다. 기존 구독·변경 이력을 삭제해 초기화하는 방식으로 적용하지 않는다.

### 01-5. 준비·승인·확정 순서로 나눈다

1. [ ] 스케줄러가 구독 ID와 최초 조회한 납기를 전달하게 한다.
2. [ ] 준비 트랜잭션에서 현재 상태·납기·해지 예약을 재확인하고 작업과 고정 요청 식별자를 저장한다.
3. [ ] 작업을 커밋한 후 외부 승인 호출을 수행한다. flush만 하고 아직 커밋하지 않은 상태로 요청하지 않는다.
4. [ ] 조건부 상태 갱신 또는 짧은 행 잠금으로 한 실행만 작업을 선점한다. DB 잠금은 외부 승인 대기 내내 유지하지 않는다.

7. [ ] 타임아웃은 UNKNOWN으로 보내고 확정 거절만 실패 정책으로 처리한다. DB 장애로 UNKNOWN 기록마저 실패하면 남은 PROCESSING을 복구 대상에 포함한다.
8. [ ] 오류 로그를 활성화하고 작업 ID·구독 ID·오류 종류를 남긴다. 승인 완료 메일은 성공 커밋 이후로 옮긴다. 메일 신뢰성 개선을 별도 프로젝트로 확대하지 않는다.

공식 멱등키 보장 범위와 유효기간을 확인한다. 기간이 지난 미확정 작업에 새 키로 무조건 청구하지 않는다. [토스 멱등키](https://docs.tosspayments.com/reference/using-api/authorization), [자동결제·조회 API](https://docs.tosspayments.com/reference)

### 01-6. 중단 복구와 상태 경합을 처리한다

- [ ] 오래된 PROCESSING과 확인 시각이 된 UNKNOWN을 찾는 복구 메서드를 만든다.
- [ ] 저장된 orderId로 승인 상태를 조회한다. 승인 확인 시 앞의 성공 확정 메서드를 재사용한다.

- [ ] 중복 작업 생성의 UNIQUE 충돌은 기존 작업 조회로 처리한다. 이미 실패한 트랜잭션 안에서 계속 조회하지 않게 경계를 나눈다.

- [ ] 청구 선점과 해지 예약의 기준 시점을 정한다. 두 경로가 동일한 DB 조정 규칙을 사용하도록 확인한다. 아직 선점 전인 해지 예약은 청구하지 않는 것으로 시작한다.
- [ ] 수동 확인은 미확정 작업 조회 → 결제사 결과 확인 → 같은 확정 메서드 적용 순서로 기록한다. 인증 없이 호출 가능한 재처리 엔드포인트를 만들지 않는다.

### 02-2. 정책을 고정한다

| 항목 | 이번 구현의 출발 정책 |
|---|---|
| 대상 | 동일 guest_token |
| 윈도 | 최초 허용 요청부터 24시간, 후속 요청으로 연장하지 않음 |
| 사용량 | 성공한 체험 + 처리 중 예약 합계 최대 3 |
| 모든 AI 폴백 실패 | 같은 윈도의 해당 예약을 한 번 반환 |
| AI 성공 후 결과 저장 실패 | 사용권을 자동 반환하지 않고 구분된 오류 안내 |
| 한도 저장소 장애 | 호출 전이면 503, AI 실행 중단 |
| 상한 초과 | 429 + 남은 TTL에 따른 Retry-After |

- [ ] 실패 반환이 있으므로 실제 시도와 공급자 호출은 3회를 넘을 수 있다고 적는다.
- [ ] 입력 오류와 비용 없는 사전 검증은 예약 전에 처리한다.

### 02-3. 같은 요구로 DB와 Redis를 비교한다

| 후보 | 같은 정책을 구현하는 방법 | 이점 | 감수할 점 |
|---|---|---|---|
| DB 카운터 | 토큰별 count·windowId·expiresAt, 조건부 갱신/잠금, 반환 식별 | 기존 DB·영속 기록 활용 | 만료·반환·동시 갱신을 설계해야 함 |
| Redis 상태 | 토큰별 상태, TTL, 허용·반환 스크립트 | 이미 게스트 결과를 저장하는 Redis 활용, 수명 관리 단순화 | 장애 의존·메모리·키 유실·스크립트 복잡도 |

- [ ] DB는 자정 배치 없이도 논리 만료를 구현할 수 있음을 적는다. 삭제 배치의 필요 여부와 유효기간 판정은 구분한다.
- [ ] 현재 Redis 재사용을 기본 선택으로 한다. 선택 이유는 기존 결과 저장소와 수명 정책이며, 성능 우위는 측정한 경우에만 쓴다.
- [ ] DB 대안을 구체화하려면 테스트용 테이블과 동시 조건부 갱신 실험을 만든다. 이는 대안 검증용이며 운영 DB로 왕복 이전할 필요는 없다.
- [ ] DB/Redis 저장소 성능까지 비교한다면 둘 다 같은 만료·예약 반환·동시성 정책을 구현한 범위를 비교한다. 기능이 다른 카운터만 비교해 전체 우위를 주장하지 않는다.

### 02-4. 사용권 관리와 키 전환을 구현한다

1. [ ] `GuestQuotaService`로 예약·반환을 분리한다. AI·결과 저장 흐름은 기존 서비스가 조정한다.
2. [ ] 허용 결과에 allowed, windowId, reservationId, remaining, retryAfterSeconds를 담는다.
3. [ ] 새 키 버전에서 토큰별 사용량·윈도·예약 식별자를 저장한다. 단일 키에서 원자화할 수 있는 구조로 시작한다.
4. [ ] 기존 문자열 키를 Hash 명령으로 바로 읽지 않는다. 전환 기간에는 기존 count와 남은 TTL을 보존해 새 상태로 옮기는 규칙을 만든다.
5. [ ] 전환 중 새 요청을 멈추고 진행 중 요청을 배출한 뒤 구버전 서버를 모두 종료하는 방식으로 단순하게 적용한다. 구·신버전이 서로 다른 카운터를 동시에 쓰지 않게 한다.
6. [ ] 기존 키에 TTL이 없거나 형태가 잘못됐을 때 임의로 무료 횟수를 초기화하지 말고 복구 대상 오류로 기록한다.

기존 활성 게스트가 없는 폐기 가능한 테스트 환경에서는 초기화를 선택할 수 있다. 이 경우 사용자 이력을 승계한 배포로 설명하지 않는다.

### 02-5. 허용과 반환을 각각 원자화한다

- [ ] 짧은 Lua 스크립트로 한도 확인 → 예약 등록·증가 → 최초 TTL 설정 → 남은 TTL 반환을 한 번에 수행한다.
- [ ] 상한 초과 요청은 카운터를 계속 증가시키지 않고 거절한다. null·스크립트 오류를 허용 1회로 해석하지 않는다.
- [ ] 반환은 키 존재·windowId 일치·reservationId 존재를 확인한 경우에만 예약을 제거하고 한 번 감소시킨다.
- [ ] 이미 만료됐거나 반환됐거나 다른 윈도이면 값을 생성하거나 감소시키지 않는다. 사용량이 0이 되어도 원래 윈도 종료 시각을 유지한다.
- [ ] AI 성공 이후의 결과 저장 실패를 모든 AI 실패와 구분한다. 반환 중 Redis 장애도 별도로 기록한다.
- [ ] 프로세스 중단으로 반환하지 못한 예약은 원래 TTL까지 남을 수 있다는 한계를 기록한다. 별도 영속 작업 시스템으로 확대하지 않는다.

- [ ] 결제에는 승인 응답 유실/DB 실패 복구 증거, 게스트에는 한도·TTL 증거, 통계에는 실제 부하 비교값을 대표 증거로 고른다.
- [ ] 상세 문서는 저장소의 재현 스크립트·테스트·결과로 연결한다. PDF에만 숫자를 쓰지 않는다.
- [ ] 결과 표에는 측정 환경·데이터·부하 조건을 짧게 병기한다. 정보가 안 들어가면 페이지를 늘리고 글씨를 과하게 줄이지 않는다.

### C-3. 마지막에 표현과 사실을 점검한다

- [ ] 분산 잠금을 구현하지 않았으면 잠금을 걸었다고 쓰지 않는다.
- [ ] `@Transactional`로 외부 결제도 롤백된다고 쓰지 않는다.
- [ ] 쿠키 토큰 제한을 사람별 총비용 상한으로 쓰지 않는다.
- [ ] 조회 횟수·응답 시간·동시 요청 수는 실제 결과에서 가져온다.
- [ ] 추가한 기술 이름만 쓰지 말고 왜 선택했는지와 대가를 함께 적는다.
- [ ] PDF 2쪽의 패키지 구조·기간·배포 주소와 3쪽의 사례 범위가 맞는지 확인한다.
- [ ] 최종 PDF를 다시 렌더링해 3개 블록의 글자 크기·줄바꿈·잘림·링크를 확인한다.
